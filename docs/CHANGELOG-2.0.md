## 2. 四个交付模块

### 2.1 历史快照（保存前面修改的配置）

- 触发：`localStorage.setItem('naraka-souljade-v1')` 被调用（钩住主引擎的 `save()`），
  外加 700ms 签名的轮询兜底 —— 无论从哪个入口改（点魂玉 / 拖拽 / 改词条 / 改参数 / 载入推荐 / 导入链接）都能抓到。
- 去重：签名 = `参数键 + 每槽 [魂玉id:染色:4词条id:4实际数值]`。
  - 与上一条相同 → 直接跳过（连续拖动滑块不会灌满历史）
  - 历史上某条相同 → 只把那条的时间戳提前，不新增
- 上限：120 条；写 localStorage 失败（配额）时按 60% 截断后重试，再失败降到 40 条。
- 每条记录自带当时的指标快照（DPS / 相对基准 / 评分 / 攻击力 / 双暴 / 各分项 DPS / 魂玉列表），
  列表里直接显示，不用回算。

### 2.2 自动保存的最高配置

- 全历史（含手动标记、导入、求解结果）里按 `metrics.dps` 取最大，独占 `best` 槽位。
- 规则：**`>` 才替换**（带 1e-9 容差），值相等不抖动写盘。
- 可锁定：锁定后任何来源都不会覆盖，只接受手动「较高者记为最高」。
- 记录升级链：`prevDps` 保留上一记录，卡片上显示「上一记录 XXX/s」。
- 可切换口径（DPS / 魂玉评分），切换后点「重算」按新口径重新扫历史。

### 2.3 动态对比（不落盘）

- `freeze A` / `freeze B` 把当前工作区快照进内存对象 `store.volatile.{a,b}`。
- 全程不碰 localStorage —— E2E 用「操作前后 key 集合完全相同」验收。
- 刷新页面即消失（符合「动态对比不需要保存」）。
- 支持 互换 A/B、清空动态、A/B 任选（当前 / 最高 / 动态 / 任一条历史）。

### 2.4 差异对比

对比粒度到**词条位**和**词条实际数值**：

| 差异类型 | 展示 |
|---|---|
| `add` / `remove` | 槽位 N 新增 / 移除「魂玉名」 |
| `swap` | 槽位 N 换玉 A → B |
| `move` | 同一颗玉换了槽位（先按 remove/swap 归类，再事后对齐成 move） |
| `modify` | 该玉内部：染元素、4 个词条位逐格、4 个实际数值逐格 |
| `params` | 基础攻击、元素、武器、倍率、频率、双暴、开关、槽位数、条件加成 |

指标对照 18 行（DPS / 相对基准 / 评分 / 攻击力 / 双暴 / 有效暴击 / 各分项 DPS / 攻击力加成 / 元素积累 / 冷却 / 合道 / 玉数 / 词条数），
每行 `A 值 · ▲/▼ 增量 · B 值`，涨绿跌红。

## 3. 求解器（自动找最高配置）

### 3.1 搜索空间与剪枝

```
槽位 4~8 × 输出元素 3 × 武器 4 × 魂玉组合 C(34,N) × 每玉 4 词条位 × 每玉染元素
```
按游戏规则硬裁剪：

- 普通词条同玉不重复；稀有词条（合道 / 化气 / 枚卜）不限条数
- 词条数值固定取满值 —— 实际洗练值 ≤ 满值，DPS 对词条数值单调不减，**满值必然不劣**，无需枚举
- 魂玉 id 全局不重复（与主引擎 `equip()` 一致）
- 无法染元素的玉（`通用·夺魂`）强制 `element = null`

词条候选剪枝（按当前参数）：

| 剔除项 | 理由 |
|---|---|
| 非输出元素的元素词条 | 冰套里堆天雷伤害，主引擎不算分 |
| `对首领伤害`（`bossDmgOn=false` 时） | 参数里关掉了就不参与计算 |
| `远程武器招式增伤`（非火炮/弓箭） | 同上 |
| `神射值积攒效率` | 不进伤害模型（上游只做展示） |

剪枝后单玉词条组合数：**~13000 → 160**（4 格填法：C(6,k)×多重组合）。

### 3.2 求解链路

| 步骤 | 做什么 | 复杂度 |
|---|---|---|
① 词条边际 | 每个候选词条单独上场测增益，排序 | O(#cand) ≈ 10 次评估 |
② 填法模板 | 由边际生成 4 套「4 格填法」（纯数值 / 单合道 / 双合道 / 双枚卜），粗筛取最大值 | O(1) |
③ 增量贪心 | 逐位填玉，每步遍历全部未上场玉选最优，只精修选中那颗 | O(N×pool×|tpl|) |
④ 多起点重启 | 固定种子打乱候选顺序重跑贪心 3 次，跳出路径依赖 | ×4 |
⑤ 池枚举 | 单练前 14 颗的 C(14,7)=3432 套全列，模板粗排，前 16 名全枚举精修 | 粗排 160ms + 精修 ~1s |
⑥ 换玉下降 | 每槽位候选玉模板粗筛 Top-6 → 全枚举精修；每轮末尾全槽位再精修 | O(rounds×N×pool×|tpl|) |
⑦ 破坏-重建 | 单点下降卡住时抠掉 1~2 颗玉重新贪心填满（跳出「必须同换 3~4 颗」的坑） | O(C(N,k)×k×pool) |
⑧ 多口径扫 | 元素 × 武器 × 槽位全扫，输出 Top 榜 | ×口径数 |

所有评分统一走主引擎 `totals()` + `damage()`，**扩展层不复制任何公式**，
上游改模型时最优解自动跟随；评估结果按「槽位签名」缓存，重复组合不重算。

### 3.3 正确性验证

`tools/nsj-validate.js` 用暴力枚举交叉验证：单练池前 14 颗的 C(14,7)=3432 套全组合，
每套做词条坐标下降，与求解器结果对比。

```
单练池 14 颗 · 每套 7 颗 · 暴力枚举 C(14,7) = 3,432 套/口径
  ✓ ice/melee     · 求解 105,815 (3329ms) · 暴力  85,720 (2891ms) · 差 -23.44%
  ✓ thunder/melee · 求解  67,341 (2782ms) · 暴力  67,341 (2865ms) · 差   0.00%
  ✓ poison/cannon · 求解  67,341 (4061ms) · 暴力  67,341 (3702ms) · 差   0.00%
  ✓ poison/bow    · 求解  67,341 (4388ms) · 暴力  67,341 (3661ms) · 差   0.00%
最大差距 0.00%，求解器结果不劣于暴力上界
```

> 冰套 -23.44% 是求解器**更优**（暴力池按单练分排序，冰爆体系玉单练分不高被排在池外）。

### 3.4 性能

| 模式 | 口径数 | 一次求解 | 评估次数 |
|---|---|---|---|
| 快速 | 6（3 元素 × 近战/火炮） | ~9~15 秒 | ~37 万 |
| 深度 | 12（3 元素 × 4 武器） | ~40~90 秒 | ~199 万 |

主线程不阻塞：每完成一个口径 `await` 让一帧，进度条与阶段文字实时更新。

动态对比不落盘 / 差异识别（增删换位改参数）/ 词条剪枝 / 优化不劣化 / 全局求解 / 回灌 / 导入导出。

## 6. 已知边界

- 求解器按「满词条」求解；实际洗练值不足时，把求解结果载入后手动改数字即可，架构不变。
- 无明确数值的机制（流星、毒沼、三才印）上游不计入期望伤害，求解器同样不为其加权 ——
  这是上游模型的口径，不是二改引入的偏差。
- 深度模式在单核低配机器上可能跑到 90 秒以上，可切快速模式或调 `budgetMs`。
